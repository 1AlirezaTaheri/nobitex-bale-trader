# راهنمای کاربر ویندوز — فقط PAPER و SHADOW

این محصول هنوز مزیت سودآوری تأییدشده ندارد. هر هفت نسخهٔ راهبرد در وضعیت NOT VALIDATED هستند؛ تاریخچهٔ قبلی برای انتخاب و تحقیق استفاده شده و آزمون خارج از نمونهٔ پاک نیست. بله ابزار مشاهده و کنترل محلی است. ورود توکن، تغییر MODE یا گذر از بازبینی، معاملهٔ واقعی را فعال نمی‌کند. این متن توصیهٔ مالی یا تضمین محدودبودن زیان نیست.

## شروع به ترتیب

فرمان‌ها را از پوشهٔ پروژه در PowerShell اجرا کنید:

```powershell
cd C:\Users\ALIREZA\Desktop\nobitex-bale-trader
.\.venv\Scripts\python.exe -m app.doctor
```

`doctor` آفلاین است؛ به بله یا صرافی متصل نمی‌شود. FAIL یعنی مورد محلی نیازمند بررسی است؛ UNVERIFIED یعنی آن مورد آزموده نشده است. خطای تنظیم اختیاری بله باعث می‌شود ثبت عمومی با کنسول ادامه یابد؛ MODE غیر از paper اجرای محصول را مسدود می‌کند. هیچ کلید صرافی لازم نیست و نباید برای این کار اضافه شود. پیش‌فرض enabled پرتفوی و زمان‌بندی همچنان false است؛ آنها را برای SHADOW مستقل تغییر ندهید.

برای نصب اولیه فقط در صورت نیاز `setup.bat` را خودتان اجرا کنید؛ این فرمان بسته‌های از پیش سنجاق‌شده را نصب می‌کند. برای بررسی محیط موجود بدون نصب:

```powershell
.\setup.bat --check-only
```

فایل `.env` موجود بازنویسی نمی‌شود. MODE باید `paper` باشد. برای اجرای بدون بله، مقادیر BALE_BOT_TOKEN و BALE_CHAT_ID را خالی بگذارید. فایل نمونه حاوی راهنماست؛ متن راهنما یا نام متغیر را جای شناسهٔ عددی نگذارید. هیچ‌گاه محتویات `.env` را در پیام، تصویر، گزارش خطا یا مخزن عمومی منتشر نکنید. دسترسی فایل را به حساب ویندوز خود محدود کنید.

## اتصال بله، فقط با اقدام خودتان

در بازوی پدر رسمی بله بازوی شخصی بسازید و توکن را فقط در `.env` و متغیر BALE_BOT_TOKEN قرار دهید. اگر doctor قالب BALE_CHAT_ID را نامعتبر اعلام می‌کند، متن راهنما/مقدار غیرعددی آن را خودتان پاک کنید تا خط `BALE_CHAT_ID=` خالی بماند؛ یک مالک معتبر و متفاوت را برای دورزدن بررسی حذف نکنید. سپس:

```powershell
.\.venv\Scripts\python.exe -m app.bale_setup --find-chat
```

این فرمان درخواست رسمی getMe/getWebhookInfo/getUpdates می‌فرستد، اما پیام آزمایشی نمی‌فرستد. عبارت یک‌بارمصرف `/setup ...` را که همان‌جا نمایش داده می‌شود در گفتگوی خصوصی بازوی خود بفرستید. فقط پیام تازهٔ همان عبارت، از فرستندهٔ واقعی همان گفتگوی خصوصی پذیرفته می‌شود. شناسه‌ها چاپ نمی‌شوند و فقط شناسهٔ تأییدشده در `.env` ذخیره می‌شود. اگر مالک قبلاً متفاوت ثبت شده یا وب‌هوک فعال باشد، عملیات خودکار آن را تغییر نمی‌دهد. برای این پروژه از بازوی اختصاصی استفاده کنید؛ هم‌زمان چند مصرف‌کنندهٔ getUpdates اجرا نکنید.

اکنون خودتان فرمانی را اجرا کنید که واقعاً پیام می‌فرستد:

```powershell
.\.venv\Scripts\python.exe -m app.bale_setup --test
```

پذیرش درخواست توسط API با دیدن پیام در گوشی یکسان نیست؛ پیام را در بله بررسی کنید. فقط موفقیت پاسخ این فرمان رسید محلی `.bale_verified.json` می‌سازد. رسید شامل خود توکن یا شناسه نیست و با تغییر تنظیمات بی‌اعتبار می‌شود. اجرای محصول با گزینهٔ `--bale` بدون رسید معتبر صرفاً کنسولی است. در مرحلهٔ توسعه هیچ‌یک از این فرمان‌ها علیه بلهٔ واقعی اجرا نشده است.

خطای 401 معمولاً نیازمند بررسی توکن است؛ 403 یعنی دسترسی رد شده و 429 محدودیت درخواست است. هیچ متن خام پاسخ، آدرس حاوی توکن یا شناسه‌ای برای عیب‌یابی ارسال نکنید. فرمان find-chat وب‌هوک را حذف نمی‌کند. پیام‌های زمان اجرای قبلی، فوروارد، ویرایش‌شده، گروهی، ناشناس و فرمان‌های خارج از فهرست بی‌پاسخ کنار گذاشته می‌شوند. فرمان‌های ثانیهٔ شروع نیز برای جلوگیری از بازپخش پذیرفته نمی‌شوند.

## اجرای SHADOW و گزارش

```powershell
.\run_shadow.bat
```

ریشهٔ پیش‌فرض `reports\final_product\shadow_v2` و آزمایش `product-shadow-v2` است. اسکریپت بله را درخواست می‌کند، اما همان رسید و تنظیمات باید معتبر باشند. اجرای مستقیم فقط کنسولی:

```powershell
.\.venv\Scripts\python.exe -m app.product_shadow
.\.venv\Scripts\python.exe -m app.product_weekly
```

در پنجرهٔ دیگری می‌توانید گزارش هفتگی را بسازید و پس از آزمون صریح، ارسال بله را درخواست کنید:

```powershell
.\run_weekly_report.bat
```

هر گزارش پوشهٔ تازهٔ `weekly_...` دارد: JSON/CSV، متن انگلیسی و فارسی و نمودار PNG واقعی. هیچ گزارش قبلی بازنویسی نمی‌شود. صفر مشاهده با متن صریح «دادهٔ آینده‌نگر نداریم» نمایش داده می‌شود؛ ماندهٔ اولیهٔ ۱۰۰ USDT سود نیست. ارقام بر مبنای USDT شبیه‌سازی هستند، نه سود ریالی/تومانی، موجودی واقعی یا قیمت قابل اجرا. دادهٔ FX و تفاوت واحدهای IRT/IRR هنوز کامل تأیید نشده‌اند.

## معنی پیام‌ها و فرمان‌ها

| پیام یا فرمان | رفتار |
|---|---|
| شروع/پایان | وضعیت فرایند محلی؛ تضمین تحویل پیام یا سود نیست |
| ثبت واقعی | یک مرز روزانه در زمان مجاز واقعاً مشاهده و ذخیره شده است |
| هشدار شکاف | حداقل یک مرز مشاهده نشده؛ هیچ معاملهٔ ازدست‌رفته بازسازی نمی‌شود |
| ضربان هر چهار ساعت | فرایند زنده است؛ سالم‌بودن همهٔ قیمت‌ها یا وجود معامله را ثابت نمی‌کند |
| گزارش روزانه | خلاصه در تغییر روز UTC، فقط وقتی فرایند در حال اجرا باشد |
| `/status` | وضعیت مکث، شمارش ثبت، وقفه و خلاصهٔ حساب‌ها |
| `/help` | فهرست فرمان‌های مجاز |
| `/pause` | ثبت مرزهای تازه را متوقف می‌کند؛ دارایی شبیه‌سازی قبلی را نقد نمی‌کند |
| `/resume` | مکث را برمی‌دارد؛ مرز بعدی را منتظر می‌ماند، عقب‌گرد نمی‌کند |
| `/stop` | فایل KILL در همین ریشه می‌نویسد و فرایند SHADOW پایان می‌یابد؛ هیچ سفارش صرافی لمس نمی‌شود |
| `/report` | خلاصهٔ فعلی؛ برای فایل و نمودار کامل، فرمان هفتگی ویندوز را اجرا کنید |

وقتی اعلان صف پر شود، API قطع باشد یا بارگذاری تصویر شکست بخورد، کنسول و گزارش محلی مرجع هستند. ارسال تضمین‌شده، صف پایدار پیام و تحویل دقیقاً یک‌باره ادعا نمی‌شود. ارسال پیام خودکار برای جبران timeout تکرار نمی‌شود، چون شاید درخواست اول تحویل شده باشد. دریافت فرمان با فاصلهٔ افزایشی حداکثر ۶۰ ثانیه ادامه می‌یابد. فایل لاگ چرخشی `logs\operations.jsonl` داخل ریشه تا چهار فایل حدوداً یک‌مگابایتی محدود می‌شود؛ snapshots و گزارش‌ها برای حفظ شواهد خودکار پاک نمی‌شوند، پس فضای دیسک را پایش کنید.

کنترل محلی در صورت قطع بله، از پوشهٔ پروژه:

```powershell
New-Item -ItemType File -Path .\reports\final_product\shadow_v2\PAUSE
Remove-Item .\reports\final_product\shadow_v2\PAUSE
New-Item -ItemType File -Path .\reports\final_product\shadow_v2\KILL
```

برای شروع دوباره پس از `/stop`، ابتدا پایان فرایند را بررسی کنید، سپس فقط فایل KILL همین آزمایش را دستی حذف و run_shadow.bat را اجرا کنید. KILL قدیمی `data\KILL` مربوط به موتور قدیمی است و کنترل این آزمایش مستقل نیست. Ctrl+C نیز برای توقف محلی قابل استفاده است. فایل قفل را هنگام فعال‌بودن فرایند حذف نکنید.

## خواب، بستن در لپ‌تاپ، به‌روزرسانی و شکاف

مرز روزانهٔ ثبت‌شده در مشخصات فعلی 20:30 UTC است؛ تا ۶۰ ثانیه پس از آن پذیرفته می‌شود. راه‌اندازی در میانهٔ روز معاملهٔ تاریخی تولید نمی‌کند. دست‌کم ۳۰۰ کندل واقعی و پیوسته برای گرم‌شدن لازم است و گرم‌شدن مشاهدهٔ آینده‌نگر نیست. هر زمان ساعت عقب برود، جهش نامتناسب با ساعت یکنواخت دیده شود، دیتابیس خراب باشد، دیسک کم باشد یا کندل بسته‌شدهٔ ثبت‌شده بازنگری شود، ثبت متوقف/رد می‌شود.

اگر دستگاه بخوابد، خاموش شود، اینترنت قطع باشد یا Windows Update راه‌اندازی مجدد کند، مرز ممکن است از دست برود. زمان‌بند بعداً می‌تواند فرایند را اجرا کند، اما مشاهدهٔ ازدست‌رفته را برنمی‌گرداند. قرار نیست تاخیر بیدارشدن یا قیمت بازگشایی جعلی پر شود. بازده اقتصادی شامل مواجههٔ قبلی در زمان خاموشی است؛ بازده پاک آن بازه null می‌شود و وقفه مانع PASS پیوسته است. وقتی هنوز هیچ ثبت واقعی وجود ندارد، ساعت بازبینی شروع نشده است.

در Power Options حالت متصل به برق، خواب و رفتار در لپ‌تاپ را مطابق شرایط واقعی خود تنظیم کنید؛ دستگاه باید تهویهٔ ایمن داشته باشد. هیچ تنظیم برق، در لپ‌تاپ یا Update در این مرحله خودکار تغییر نکرده است. WakeToRun به پشتیبانی سخت‌افزار و سیاست سیستم وابسته است؛ روشن‌کردن رایانهٔ خاموش یا اجرای موفق را تضمین نمی‌کند. هم‌زمانی تاریخ محلی با ۲۵ نوامبر ۲۰۲۶ تأیید مستقل UTC نیست.

## تنظیم Task Scheduler

این کارها ثبت نشده‌اند و باید توسط خودتان انجام شوند. Task Scheduler → Create Task:

1. نام `NobitexShadowV2`، حساب ویندوز خودتان، گزینهٔ Run only when user is logged on؛ دسترسی بالاتر لازم نیست.
2. Trigger برابر At log on برای حساب خودتان؛ این حالت قبل از ورود کاربر فرایند را اجرا نمی‌کند.
3. Program برابر `C:\Windows\System32\cmd.exe`، Start in برابر `C:\Users\ALIREZA\Desktop\nobitex-bale-trader` و Arguments دقیق زیر:

```text
/d /c ""C:\Users\ALIREZA\Desktop\nobitex-bale-trader\run_shadow.bat""
```

4. در Settings اجرای دوباره پس از شکست با فاصلهٔ یک دقیقه و حداکثر سه مرتبه، و If task is already running برابر Do not start a new instance. گزینهٔ توقف پس از چند روز را برای ثبت پیوسته بردارید. محدودیت برق/باتری را آگاهانه انتخاب کنید.
5. برای کار `NobitexShadowWeeklyV2` همین Program و Start in، Trigger هفتگی یکشنبه ساعت 09:00 محلی، و Arguments زیر را بگذارید. محدودیت اجرای ۱۰ دقیقه، Start when available و Wake the computer را در صورت نیاز فعال کنید؛ اینها جبران مرز مشاهده نیستند.

```text
/d /c ""C:\Users\ALIREZA\Desktop\nobitex-bale-trader\run_weekly_report.bat""
```

6. ابتدا خودتان Run را بزنید و History، Last Run Result، کنسول و زمان آخرین گزارش/ثبت را بررسی کنید. یک دور خروج/ورود ویندوز، یک خواب/بیداری و یک restart را با سرمایهٔ واقعی صفر بررسی کنید. این آزمایش‌های فیزیکی در این مرحله انجام نشده‌اند.

کلید/توکن را در Arguments، نام task یا متغیرهای زمان‌بند نگذارید. بدون کاربر واردشده، اتصال برق، شبکه و فرایند فعال، ثبت پیوسته ادعا نشود. آموزش رسمی Microsoft برای WakeToRun/StartWhenAvailable در فهرست منابع پژوهش است.

## تحمل افت سرمایه و گزینهٔ دستی

متن اصلی گزارش ۷ ژوئیهٔ ۲۰۲۶ Wells Fargo Investment Institute، با دادهٔ روزانه تا ۱۷ ژوئن ۲۰۲۶، افت حدود ۸۳٪ بیت‌کوین از ۱۷ دسامبر ۲۰۱۷ تا ۱۴ دسامبر ۲۰۱۸ و حدود ۷۷٪ از ۹ نوامبر ۲۰۲۱ تا ۲۱ نوامبر ۲۰۲۲ را گزارش کرده است. پاورقی‌های ۲ و ۳ همان صفحه با متن اصلی ناسازگاری تاریخ دارند؛ بنابراین اینها فقط نقل تقریبی از متن اصلی‌اند و اینجا مستقلاً بازسازی نشده‌اند. منبع R16 و این محدودیت در `RESEARCH/BIBLIOGRAPHY.md` ثبت شده‌اند. افت آینده می‌تواند بیشتر، حتی از دست رفتن کامل دارایی، باشد. افت روزانهٔ بسته‌شدن کندل خطر درون‌روزی را کمتر نشان می‌دهد.

ابتدا مبلغی را که برای مخارج ضروری/بدهی لازم دارید از تصمیم پرریسک جدا کنید و زیان قابل تحمل را به پول واقعی بنویسید. رابطهٔ آموزشی ساده، با فرض ثابت‌ماندن بخش امن و بدون هزینه/بازتنظیم، `w × s` است: سهم دارایی پرریسک ضرب‌در افت آن. برای سناریوی ۸۵٪ افت و سناریوی ازبین‌رفتن کامل:

| زیان قابل تحمل کل | سهم محاسباتی با افت ۸۵٪ | سهم محاسباتی با زیان ۱۰۰٪ |
|---|---:|---:|
| ۵٪ | حدود ۵٫۹٪ | ۵٪ |
| ۱۰٪ | حدود ۱۱٫۸٪ | ۱۰٪ |
| ۲۰٪ | حدود ۲۳٫۵٪ | ۲۰٪ |

این جدول تخصیص پیشنهادی یا سقف زیان نیست. بازتنظیم در روند نزولی، کارمزد، لغزش، همبستگی ETH/BTC، خطر صرافی و خود USDT فرض ساده را نقض می‌کنند. نگهداری بقیهٔ دارایی در USDT داخل همان صرافی به معنی بخش امن یا تضمین اصل پول نیست. کمترین زیان و سود قطعی هم‌زمان قابل تضمین نیستند.

گزینهٔ کم‌نیاز به نگهداری: سهمی را پیش از مشاهدهٔ نتیجه و متناسب با توان زیان خود تعیین کنید، ماهی یک بار در تاریخ مشخص وزن واقعی/هزینه/نیاز نقدینگی را دستی بررسی کنید و فقط با قاعدهٔ از پیش نوشته‌شده تصمیم بگیرید. B4های پژوهش برای مقایسه ماهانه با انحراف مطلق ۵ واحد درصد هستند؛ هیچ‌یک توصیه نشده‌اند. B3 از همان ۱۰۰ USDT اولیه ماهانه ۱۰۰/۱۲ را تا تمام‌شدن وجه به کار می‌برد؛ واریز خارجی یا پس‌انداز ماهانهٔ حقوق نیست. افزایش تعداد معاملات یا استفاده از مدل زبانی دلیل سودآوری نیست.

## ارزیابی، تغییر نسخه و موارد لازم برای LIVE

بازبینی‌ها در ۳، ۶ و ۱۲ ماه تقویمی از نخستین ثبت واقعی و با حداقل ۸۰، ۱۶۰ و ۳۲۰ بازهٔ مشاهده‌شده‌اند. معیارها همان افت حداکثر ۶۰٪ افت B1، بازده حداقل B7 علّی منهای دو واحد درصد، هزینه حداکثر ۲۵٪ سود ناخالص مثبت و نبود وقفه‌اند. PASS فقط ادامهٔ مشاهده است. مقایسهٔ ریسک با هر سه B4 نشان داده می‌شود؛ نزدیک‌ترین افت تحقق‌یافته برچسب پس‌نگر دارد و برای انتخاب قابل معامله معتبر نیست. دوازده ماه نیز می‌تواند فقط یک رژیم باشد.

پارامتر، فایل‌های اثرانگشت یا نسخه را روی ریشهٔ قبلی عوض نکنید؛ کد ناسازگار باید ریشه و ساعت مشاهدهٔ جدید داشته باشد. ریشه‌های قدیمی و manifestها را نگه دارید. حداقل هفتگی آخرین هش گزارش را در محل مستقلی که همان رایانه نتواند بی‌ردپا بازنویسی کند نگهداری کنید. زنجیرهٔ محلی، اصالت در برابر بازنویسی کامل یا حذف انتهای کل تاریخ را تضمین نمی‌کند. این مستقل‌سازی در این مرحله انجام نشده است.

LIVE هنوز نیازمند همهٔ این موارد است: قرارداد رسمی و آزموده‌شدهٔ احراز هویت/دسترسی سفارش؛ حداقل سفارش، گردکردن، واحدها و کارمزد واقعی؛ client-ID و idempotency؛ وضعیت سفارش در timeout و reconciliation پس از restart؛ پرشدن جزئی/لغو/لغو ناموفق؛ حفاظت واقعی هنگام خاموشی؛ دفتر و قیمت اجرای معتبر و محدودیت API؛ مجوز/مقررات/مالیات قابل اعمال؛ محدودیت و امنیت کلیدها؛ تست نفوذ/آسیب‌پذیری مستقل؛ تحمل خطای سخت‌افزار/شبکه؛ شواهد کافی آینده‌نگر در چند رژیم و بازبینی انسانی مستقل. هیچ checkbox یا تغییر YAML جای این موارد را نمی‌گیرد. حمل‌ونقل ارسال/لغو واقعی عمداً مسدود است.
